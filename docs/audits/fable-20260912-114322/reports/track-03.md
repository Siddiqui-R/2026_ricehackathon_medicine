### RVA-03-001 — P2 · candidate · confidence high — Startup repair save failure hides a valid loaded snapshot and offers only an unconfirmed demo reset

- **Files/lines:** `apps/ios/Reva/State/AppStore.swift:58–86` (repair mutations at 65–71 and 72–82 inside the load `do`; `catch` at 86 sets `startupError`), `apps/ios/Reva/State/AppStore.swift:111–116` (`mutate` throws from `repository.save` before publishing), `apps/ios/Reva/Features/Shared/RootView.swift:21–29` (whole UI replaced by the error screen; the only action is `store.resetDemo()` with no confirmation dialog, unlike `SettingsView.swift:99–102`), `apps/ios/Reva/State/AppStore.swift:138` (the only place `startupError` is cleared).
- **Trigger:** `LocalRepository.load()` succeeds and the loaded snapshot contains either the legacy demo title `"Nausea and palpitation diary - date needs review"` on `demo-record-symptom-diary` or a non-live booking in `queued`/`calling` status (an interrupted simulation), and the repair write fails — for example `state.backup.json`/`state.json` cannot be written because device storage is full, or the backup path is unwritable.
- **Expected:** A valid snapshot that loaded successfully stays usable; a cosmetic/repair write failure is reported as a non-blocking error (or deferred) and the destructive reset remains a confirmed, explicit action.
- **Actual:** `snapshot` is already set (line 60) when `save(sample)`/`mutate` throws; the throw lands in the shared `catch` (86), `startupError` becomes the raw filesystem error text, `RootView` shows "Your data needs attention" with a single prominent "Restore fictional demo" button that runs `resetDemo()` immediately. `resetDemo()` replaces the active state with the seed (`AppStore.swift:136–137`); the previous state survives only as the single backup until the next save overwrites it, and no UI restores from backup.
- **Impact:** Under a plausible device condition (storage exhausted at launch) the user is blocked from valid data and steered to a one-tap action that discards it. Data loss requires the user tap, and one backup generation remains, which is why this is rated P2 rather than P1/P0; validators may reasonably escalate given the missing confirmation.
- **Evidence:** Source proof above. Refutation attempts: (a) checked whether `didSet`/publication ordering could leave `snapshot` nil — no, line 60 runs before either repair; (b) checked whether any other code clears `startupError` — only `resetDemo` (grep over `apps/ios`); (c) checked whether `RootView` gates the error screen on anything else — it does not (21); (d) the seed already carries the new title (`demo/seed.json`), so the rename repair only affects older installs, but the booking repair applies to any interrupted simulation. Not reproduced at runtime; see ER-03-5.
- **smallestFix:** Move the two repair mutations out of the load `do/catch` into their own `do { … } catch { errorMessage = … }` (or `notice`) so `startupError` is reserved for load failures; additionally wrap the RootView reset in the same confirmation dialog Settings uses.
- **regressionCheck:** In the OptimizationChecks style, save a fixture containing a `queued` non-live booking to a temp `LocalRepository`, make `state.backup.json` a directory, construct `AppStore(repository:)`, assert `startupError == nil`, `snapshot != nil`, `errorMessage != nil` (or notice), and that the booking still reads `queued` (repair deferred, not lost).
- **ownerTrack:** Captain (shared core state).

### RVA-03-002 — P3 · suggestion · confidence high — 409 handling discards the server's `X-State-Revision` and fetches the whole snapshot to learn the conflict revision

- **Files/lines:** `apps/ios/Reva/Core/ServerClient.swift:108` (`409` mapped to `ServerFailure.conflict` with no payload, although the server sets `X-State-Revision` on 409 at `server/Sources/RevaServer/HTTP.swift:50–53`), `apps/ios/Reva/State/AppStore+Sync.swift:111–125` (secondary `pull()` whose snapshot body is discarded; on any secondary failure `serverConflictRevision = nil`, which hides the "Replace server" control).
- **Trigger:** Any push that returns 409.
- **Expected:** Conflict revision read from the header already received; one round trip.
- **Actual:** A second `GET /v1/state` (up to the 4 MiB snapshot cap, `server/Sources/RevaServer/Models.swift:125`) is issued solely to read `revision`; if that GET fails transiently, the explicit overwrite option disappears until the user retries the push.
- **Impact:** Bounded: at most one extra 4 MiB GET per conflict on a developer/demo transfer path; a transient failure costs the user one extra retry. No data risk.
- **Evidence:** Source proof above; `TransportTests.testConflictDoesNotRetryOrModifySnapshot` (TransportTests.swift:193–210) already sends `X-State-Revision: 11` on a 409 and only asserts `.conflict`.
- **smallestFix:** Make `ServerFailure.conflict` carry `Int?` parsed from `X-State-Revision` (mirroring `.empty`) and use it in the handler, keeping the secondary pull only as a fallback when the header is absent.
- **regressionCheck:** Extend the existing transport test to assert the parsed revision; add a StateChecks case where `onPush` throws `.conflict(11)` and assert `serverConflictRevision == 11` with `pull` never called.
- **ownerTrack:** Captain (shared client transport); coordinate with Person 3 for the header contract, which already exists.

- **ownerTrack:** Captain (shared core persistence).

### RVA-03-004 — P3 · suggestion · confidence high — Push replaces server attachment bytes before the CAS snapshot write; pull refuses the same situation, so the system is asymmetric (documented tradeoff, hardening proposed)

- **Files/lines:** `apps/ios/Reva/State/AppStore+Sync.swift:53–65` (uploads precede `client.push`), `server/Sources/RevaServer/HTTP.swift:137–154` and `LocalFileStore.swift:109–122`, `PostgresStore.swift:116–137` (`putAttachment` unconditionally replaces by `(owner, sha256(filename))`), `apps/ios/Reva/Core/LocalRepository.swift:71–77` (pull refuses different bytes under an existing name). Documentation: `README.md:70`, `docs/architecture.md:202`, `apps/web/src/core/COMPATIBILITY.md:22` ("failed/conflicting pushes can leave uploaded or overwritten attachment bytes on the server").
- **Trigger:** Two clients of one owner hold different bytes under the same filename; one pushes and gets 409.
- **Expected (per F05 assessment):** Either an explicit tradeoff or a concrete defect. Assessment: **documented tradeoff**. Same-name/different-bytes has no first-party producer: native import names are `UUID-<name>` (`AddRecordView.swift:264`), recordings `recording-<UUID>.m4a` (`AudioServices.swift:133–134`), browser import `${uid()}-…` (`ImportDialog.tsx:125`) and `reva-audio-${id}` (`RecordingCapture.tsx:113`); bundled fixture names are shared across clients but the bytes are identical (`demo/sources` vs iOS `Resources`: 11/11 SHA-256 equal) and the fixture files have changed in exactly one commit (`eb2ec3a`).
- **Actual residual risk:** If fixture bytes ever diverge between builds/clients, the client pushing second silently replaces the server copy referenced by the live snapshot even though its CAS fails, and the other client's next pull is refused with a message telling the user to re-import under a new filename — impossible for a bundled fixture, leaving that owner unable to pull. The accounts contract (multi-device per user) makes concurrent pushes more likely.
- **Impact:** Bounded and currently not reachable through first-party flows; the pull side fails closed, so local evidence is never replaced.
- **Evidence:** Source proof above; documentation lines quoted.
- **smallestFix:** Server-side: let `PUT /v1/attachments/:id` refuse to replace *existing different bytes* unless the client supplies an explicit override (e.g., `If-Match`/expected revision), returning 409 with the current revision; client-side: word the pull-conflict message differently for bundled fixture names. Keep fixture bytes pinned by the existing `fixture-manifest.json` hashes on both clients.
- **regressionCheck:** Server test: upload bytes A, upload bytes B under the same id without override → 409 and bytes A retained; with override → replaced. Native: existing `checkPullFiles` R2 case remains green.
- **ownerTrack:** Person 3 (server contract) with Captain for the shared client contract. Forward-looking for the accounts work; not a completed-path defect.
