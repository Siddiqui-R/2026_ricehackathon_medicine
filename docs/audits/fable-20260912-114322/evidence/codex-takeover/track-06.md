## 3. Findings (ordered by severity; full detail in `track-06-findings.json`)

### RVA-06-001 — P2 · candidate · F05 · owner: Captain (with Person 3 for any server index/prune)
**Server originals are never pruned and every referenced original is re-uploaded on each push; owner quota can be exhausted with no browser remedy.**
- Trigger: over an owner's lifetime, import and delete records (or audio memories), pushing after each; and/or several 409-conflicting pushes. Each push re-sends every referenced original; originals of deleted records and of failed-CAS pushes remain server-side forever.
- Expected: push transfers only what the server lacks and some path removes unreferenced originals so the 128-file / 64 MiB owner cap is not consumed by orphans.
- Actual: `store.ts:520-524` uploads every `originals(snapshot)` entry on every push; `api.ts:249-252` `deleteAttachment` and `224-226` `deleteState` exist but are unreachable (`APITransport`, `store.ts:23-36`, omits them; no store caller); native `AppStore` has no callers either. Server quota counts all owner attachments including orphans (`LocalFileStore.swift:110-121`, `PostgresStore.swift:120`).
- Impact: O(total referenced bytes) per push — with the checked-in seed 9 files / 618,312 bytes are re-sent on every push even when unchanged (bounded measurement from `seed.json` + `fixture-manifest.json`); after 128 distinct filenames have ever been uploaded, every further push fails with 413 and the browser has no recovery action.
- Refutation attempt: uploads overwrite by id, so bytes are not duplicated; the seed alone cannot reach the cap; therefore classed P2 candidate (long-lived owners / failed pushes), not a main-path confirmed defect.
- Smallest fix: skip originals the server already holds (probe by id or a server attachment index) and delete unreferenced ones after a successful push; or document the cap and add an explicit prune action.
- Regression: push twice unchanged → uploads once then zero; delete a record and push → `deleteAttachment` called; owner attachment count equals referenced count.

### RVA-06-007 — P2 · suggestion (forward-looking, accounts WIP) · F04, G06 · owner: Captain, coordinate with tracks 12/13
**After an identity change the first check adopts the remote revision unconditionally, so the next push replaces that identity's server snapshot with the local (possibly demo) workspace.**
- `setToken` (`store.ts:182-193`) nulls `serverRevision`; `checkServer` (`486-509`) adopts the remote revision when `known === null` and reports only "Provider availability checked."; `pushToServer` (`510-540`) then succeeds with that base revision. The local DB name is token-independent (`repository.ts:59`).
- Not a defect today: the Settings copy states push "Replace[s] the server's snapshot" (`SettingsPage.tsx:95-98`). Under the accounts contract (per-user IndexedDB name, 1.5 s auto-push), reusing `pushToServer` after login without a required pull could push a demo workspace into a real account.
- Smallest fix: remember per identity whether this browser has pulled or pushed once; if the first check finds a non-tombstone remote snapshot, set `mustPull` (or require an explicit "replace server copy" confirmation). Regression: store test — new identity with remote revision 5 → check → push rejects until pull succeeds.

### RVA-06-002 — P3 · evidence-gap · F03 · owner: Captain

The algorithms match by inspection (`domain.ts:78-90` vs `ReportEngine.swift:33-44`), so the risk is provenance, not a known mismatch. Fix: put the hashes in a shared fixture asserted by both suites, or record the Swift output (evidence request ER-06-2).

### RVA-06-003 — P3 · suggestion · B02 · owner: Captain
**Persistence depends on transport, and features bypass the injected persistence through module-level attachment helpers.** `repository.ts:7` imports `boundedBytes`/limits from `api.ts`; `repository.ts:287-290` exports a singleton used directly by four feature files, so an injected `SnapshotRepository` never sees attachment IO. Fix: leaf `limits.ts`; expose `saveAttachment/getAttachment` on the store/context; delete the wrappers.

### RVA-06-004 — P3 · suggestion · B02 · owner: Captain
**Transfer rules duplicated in four places with different subsets** (`api.ts:32-48`, `store.ts:54-61`, `store.ts:341-350`, size checks in `repository.ts:34-38` / `api.ts:230` / `api.ts:295`). No current mismatch fails (all are subsets of server `Validation.contentTypes`), but drift is one edit away. Fix: a single media-type table and one blob check.

### RVA-06-005 — P3 · suggestion · N01 · owner: Captain
**`MemoryRepository.getAttachment` fabricates an original for unknown filenames** (`fixtures.ts:62-64`) whereas production throws "missing" (`repository.ts:204-208`); the divergence is unlabelled and push tests never seed originals, so a regression that pushes without a real original would pass. Fix: mirror the production error, seed fixtures, add one missing-original push test.

### RVA-06-006 — P3 · suggestion · H04, F04 · owner: Captain
**Attachment PUT/GET share the generic 25 s total deadline** (`api.ts:144, 232-245`) while a same-size transcription upload gets 110 s (`api.ts:302-303`). A 16 MiB original needs ≥5.37 Mbit/s sustained; because every push re-uploads everything, a slow link can never push that workspace. Data is preserved and the message is explicit, hence suggestion. Fix: size-derived or idle timeout for attachment transfers.

### RVA-06-008 — P3 · suggestion · F02 · owner: Captain
**Cold-start seeding race**: two tabs opening an empty workspace both run `commit(seed, 0)` (`store.ts:146`); the CAS loser reports the "changed in another tab… Reload" error with `snapshot: null` (`160-163`). Correct and non-destructive but avoidable: on `LocalConflictError` at seed time, `load()` again.

### RVA-06-009 — P3 · suggestion · F05, D02 · owner: Captain (Person 1 for evidence policy)
**Browser pull overwrites a same-name local original without comparing bytes** (`repository.ts:147`), whereas native `stagePullAttachment` stops the pull on conflicting bytes (`LocalRepository.swift:67-79`). Only reachable through contrived paths (shared demo token with differing fixture builds); after commit the snapshot and originals are mutually consistent and the user confirmed "Pull and replace". Recorded for parity with the documented native guard.
