# Reva hackathon prototype — binding completion criteria

Written before implementation, September 12, 2026. User goal: a presentable, functional native Swift iPhone prototype based on the Apple Health-led style plan and the supplied Ivory / Gold / Slate / Teal / Aqua / Sky palette. This file is mirrored to /Users/tempadmin/goals.txt as requested.

The objective is the full patient journey, not a static dashboard. Live AI, telephony, authentication provider provisioning, Tiger database credentials, App Store/device signing, and other user-owned external setup are explicitly deferred. The interface must honestly distinguish local/demo behavior from future live services. These exceptions do not excuse broken local flows or absent integration contracts.

## Completion gates

1. **Native executable:** a reproducible Xcode project or documented generation command builds a SwiftUI iPhone application with the installed SDK. It launches in an available iPhone simulator without crashing. The app remains native Swift; a browser substitute does not fulfill this gate.
2. **Selected visual design:** apply the supplied image's six colors as named semantic tokens, with contrast-safe text/action variants and dark appearance. Preserve Apple Health-like large titles, readable grouped sections, restrained color, and Summary / Records / Visits navigation. One Medical is excluded. Verify representative screens visually at a normal and smaller iPhone size.
3. **Complete navigation:** Summary, searchable/filterable Records, upcoming/past Visits, profile/settings, record detail, visit detail, pre-visit report, scan/upload review, booking request/status, recording/transcript, and post-visit memory are reachable. Visible actions either perform their labeled local action or clearly explain missing device/provider setup; no silent dead buttons.
4. **Persistent demo state:** seed a clearly fictional profile on first launch. Local record additions, notes/corrections, appointment creation/editing, report changes, and booking/recording state survive relaunch. Demo reset is explicit and restores a known coherent fixture set. Never read or import real medical records automatically.
5. **Records intake:** user can import PDF/text/image from Files, choose an image, or invoke native camera scanning on supported hardware. Preserve imported source in app storage and surface readable errors for unsupported/corrupt/unreadable inputs. Simulator camera limitations have a usable sample-import path. Native OCR/text extraction produces preview text where supported; no fake extraction-success claim.
6. **Record memory:** every imported usable item automatically receives a plainly labeled local/demo summary or a clear needs-review state. Users can inspect original/extracted text, edit title/date/text or notes, and delete an item. Saved source references connect records to generated reports. No claim that an unconfigured AI provider has run.
7. **Appointments and preparation:** add/edit a visit with date, timezone, provider, type, concern, goal, and questions. Generate a locally functioning report with relevant history, questions, and evidence links. Different fixture visit goals produce meaningfully different evidence selections. User-pinned records are included. Report regeneration responds to changed source or goals.
8. **Report interface/export:** readable concise sections, editable questions/notes, original-source links, and a native share/export path to a formatted PDF. Use deterministic source-based content in demo mode, not diagnostic or treatment recommendations. Inspect at least one generated PDF.
9. **Booking prototype:** user reviews a clinic number and allowed appointment constraints, starts a clearly simulated booking, sees state progression, and receives a coherent proposed/confirmed demo outcome. Support a needs-user/failure path and avoid duplicate appointments from repeated completion. No actual calls occur without provider configuration.
10. **Recording and after-visit flow:** microphone permission, start/pause/resume/finish controls, visible elapsed/recording state, saved audio where hardware permits, playback, and a transcript/post-visit summary view. Provide a clearly labeled bundled sample visit for a deterministic demo when live transcription is unconfigured. Preserve recording-relative timestamps and distinguish sample transcripts from actual recorded audio.
11. **Tiger PostgreSQL preparation:** implement a server boundary and PostgreSQL schema/migrations for all prototype domain data and source attachments (or an explicit storage strategy matching the user's Tiger choice), with ownership scoping and configuration validation. Prepare a Swift backend with CRUD/sync operations and a functioning local development mode. The app must have a tested repository/transport boundary and documented path to Tiger-backed persistence when credentials are added. Verify SQL/schema and backend behavior with meaningful tests; live Tiger access is a manual prerequisite, not falsely reported as connected.
12. **Empty configuration:** a root `.env` exists and is exactly empty; it is ignored by Git. Provide a separate `.env.example` and setup guide explaining optional fields and that no keys are embedded. No provider APIs, paid resources, purchases, live calls, DNS, or production deployment are activated during this build.
13. **Separate demo dataset:** ship a reproducible fictional dataset of multiple medical documents and at least two distinct visit scenarios, supporting source dates, medication/allergy/history context, labs, a procedure/implant where relevant, and a recorded-visit transcript. Mark sample artifacts as synthetic. Include standalone demo documents that can be imported during a presentation, fixture metadata, and a short demo script.
14. **Robust basic behavior:** search/filter, empty/error/processing/partial states, input validation, owner-scoped server operations, atomic/recoverable local persistence, stale report behavior after record mutation, and duplicate-call/job handling are exercised. Focus on consequential failures rather than polishing every edge case beyond hackathon scope.
15. **Review loop:** use Claude Fable 5.1 at an available high reasoning setting for at least architecture/spec review and implementation/code review, and a final focused review when feasible. Send bounded precise packets, review the returned findings manually, fix material issues, and preserve a review log with accepted/rejected findings and verification evidence. If Claude usage is exhausted, verify the reset/wait condition and continue independent work; do not pretend the review happened. No permission/security bypasses to grant access.
16. **Subtask specifications and ownership:** maintain detailed specs for delegated work, contracts and file ownership. The primary agent owns cross-feature architecture and integration, manually reviews contributions, and checks the actual app rather than relying on agent summaries.
17. **Verification evidence:** record successful build/test commands; visually inspect running core screens; exercise an end-to-end route (seed → relevant report → source → edit/import → regenerate → appointment → simulated booking → sample recording/transcript → share). Verify persistence through relaunch. Separate verified simulator behavior from physical-device-only capabilities and deferred live integrations.
18. **Delivery and checkpoints:** provide a concise README with build/run steps, known manual setup, demo flow, database/API architecture, and tested limitations. Make frequent focused Git commits, maintain a detailed completed-work/revision log, use isolated worktrees for later code reviews and targeted revisions, and push the completed work to the configured GitHub remote as explicitly requested. No website/App Store publishing is requested. Completion requires checking every gate against files and execution evidence, with explicit remaining manual steps.
19. **Final stack visualization:** immediately before the final GitHub push, write `docs/architecture.md` with readable diagrams of the actual completed app/server/database stack and the upload-to-report, booking, and recording data flows. Label functional local/demo components and deferred live integrations. Link it from the README, verify it against the final code/configuration, and include it in the final commit/push.
